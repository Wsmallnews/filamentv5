# 产品规格逻辑优化（规则定稿）

> 本文档由原始需求整理而来：把每条规则解析为 AI 可直接执行的数据流描述。
> 核心目标：**规格/变体记录的 ID 稳定性**——后续其他表会引用 `sn_product_variants.id`，
> 保存时必须按变更程度分级处理，禁止无脑「全删重建」。

1、商品编辑时不允许切换规格类型 ✅（已实现）
    1、`spec_type` 字段在编辑/查看页（record 已存在）disabled；创建页可自由选择
    2、disabled 字段不参与脱水，保存时以数据库中已有的 `spec_type` 为准，不会被动变更
    3、理由：跨类型切换意味着数据结构迁移（如多规格→单规格的变体合并），语义复杂且易出错；确需变更类型时新建商品

2、匹配键：编辑时以「数据库 ID」为准，名称仅作创建态兜底（核心约定）

    1、编辑回填（toFormState）时，规格项 / 规格值 / 变体的表单 state 均携带各自数据库 `id`（通过 repeater item 内的 Hidden id 字段随 state 存活，repeater 重写 item key 不影响 item 数据内的 id）
    2、保存（diffSync）按 id 三路匹配：
        - state 中带 id 且库中存在 → 同一记录，原地 UPDATE（改名 / 排序 / 改属性都保留数据）
        - state 中无 id → 新增记录（默认值）
        - 库中有、state 中未出现的 id → 删除记录（数据随之失效）
    3、变体记录的匹配键 = 其包含的全部子规格 id 的有序集合（通过 pivot 读取）；任一子规格无 id（新建值）→ 该组合必然是新建变体
    4、ID 方案天然消除误判：调整顺序（id 不变仅重排 order）、重命名（id 不变仅改 name）、删旧增新（无 id → 新建默认值）可任意混合，互不干扰
    5、名称兜底仅用于创建态（首次保存，所有项均无 id）与前端重算的临时保留

3、保存策略：按 id diff 自动分级的处理语义

    1、【级别 A：仅改属性值】id 集合完全不变，价格 / 库存 / 货号 / 重量 / 换算比例 / 图片变化
        → 所有 specs / variants 记录原地 UPDATE，不删除、不新增、不改排序
    2、【级别 B：改名】规格项名或规格值名变化（id 不变）
        → UPDATE 对应 spec.name；含该值的变体记录保留，`product_spec_text` 同步重算更新
    3、【级别 C：增/删规格值】规格项 id 集合不变，某项下规格值 id 集合变化
        → specs：无 id 的新值追加记录（order_column 续排）；库中消失的 id 删除记录；其余 UPDATE（order / 名称 / 图片）
        → variants：组合的子规格 id 集合在库中无对应（含被删值或含新值）→ 前者删除、后者新建；其余组合原地 UPDATE
    4、【级别 D：仅调整顺序】id 集合不变，排列顺序变化
        → 不删除任何记录
        → `sn_product_specs`：按新顺序将父级、子级 `order_column` 各自重置为连续值（0..n）
        → `sn_product_variants`：按「规格项顺序 × 规格值顺序」的笛卡尔积展开序，将 `order_column` 重置为连续值（表已加 `order_column` 字段 ✅）
        → 后续查询规格/变体列表一律以 `order_column` 为排序规则
    5、【级别 E：增/删规格项（维度变化）】规格项 id 集合变化
        → `sn_product_specs`：老记录一律保留（仅按新顺序重排 `order_column`），新增的规格项/规格值追加记录
        → `sn_product_variants`：**全部删除后重建**（组合维度变化，老组合的子规格 id 集合在库中全部失配）；重建的新组合一律使用默认值，**不继承老变体的价格 / 库存 / 货号 / 销量等任何数据**（例：颜色(红)+尺码(M) 的变体 10 元，新增规格项"材质"后，红×M×各材质 的新组合价格归 0，老数据失效）
    6、【级别 S：单规格/多单位】唯一（或按单位展开的）变体
        → 编辑时按唯一变体原地 UPDATE，不删除重建；多单位组合集合变化时按级别 C 处理

    运营字段说明：级别 E 重建时 sales（销量）等运营数据一并清零；如需保留历史销量，应通过独立的统计口径（按 product 维度或事件流水）累积，不依赖 variants 记录

4、前端重算规则（`ProductSpecForm::computeVariants`，编辑表单交互时）
    1、组合指纹优先使用**子规格 id 序列**（编辑态，id 不随改名/重排变化），无 id 的创建态退化为名称序列
        → 改名 / 重排时老组合指纹不变，已填的值与 id 原样保留（修复：目前新增规格值瞬间老值显示为 0、改名后老值丢失的 bug）
    2、新增规格值（名称未填时）触发重算：空名值被过滤，组合集合不变，所有老组合的已填值与 id 原样保留
    3、删除规格值：含该值的组合立即从列表移除，其余组合保留原值（修复：目前删除后变体列表不变的 bug）
    4、组合列表顺序 = 规格项顺序 × 规格值顺序的笛卡尔积展开序（与级别 D 的 order_column 语义一致）

5、后端保存规则（`ProductSpecService::save` 重构为 diffSync）
    1、读取数据库现状（specs 树 + variants + pivot），与表单目标态按 id 做 diff，处理语义按第 3 条各级别自然涌现，无需显式判定级别
    2、整个保存过程包裹在数据库事务中
    3、pivot 表（sn_product_spec_variants）跟随变体记录同步：删变体先清 pivot，新变体建立后 attach
    4、`product_spec_text`（组合中文名）在任何结构/名称变化后同步重算更新
    5、无论何种级别，保存后始终：重置 specs / variants 的 order_column 为连续值；同步主表 `sn_products.price` = 最低变体价格

6、补充规则（实现时需遵守）
    1、规格值名称在同一规格项内必须唯一（重算与保存均按名称去重，当前实现已满足）；id 是记录身份，名称是业务展示，两者职责分离
    2、孤儿数据清理：删除规格值/变体后，对应 pivot 记录必须同步删除，不允许出现无主关联
    3、编辑回填（toFormState）注入 id，且排序以数据库 order_column 为准，保证表单初始顺序与库中一致
    4、变体模型默认排序改为 `orderBy('order_column')->orderBy('id')`，与 specs 的排序行为对齐
